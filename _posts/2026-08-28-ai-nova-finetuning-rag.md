처음에는 Fine-tuning을 하면 회사 정보를 모델이 외우기 때문에 가장 정확한 답변이 나올 것이라고 생각했다. RAG는 그저 문서를 찾아 주는 검색 기능에 가깝다고 봤다.

하지만 AI-NOVA라는 가상의 사내 IT 환경을 대상으로 직접 실행해 보니 결과는 예상과 달랐다. 작은 데이터로 수행한 Fine-tuning은 학습이 정상적으로 끝났는데도 핵심 정보를 정확히 반영하지 못했다. 반면 RAG는 필요한 내부 문서를 검색해 답변에 사용했고, 정보가 바뀌었을 때도 재학습 없이 최신 내용을 반영했다.

이번 글에서는 코드 구조보다 실제 결과에서 관찰한 현상과 그 의미를 중심으로 정리한다.

## 실습에서 비교한 세 가지 방법

### Base Model

별도의 회사 자료 없이 모델이 원래 알고 있던 일반 지식만으로 답변한다. VPN, GPU, CPU 같은 공개된 개념은 설명할 수 있지만 회사 내부의 계정, 서버 버전, 복구 정책은 알 수 없다.

### Fine-tuning

AI-NOVA Domain Q&A 8개를 LoRA 방식으로 추가 학습했다. 모델의 일부 파라미터만 효율적으로 학습하는 방식이라 전체 모델을 다시 학습하는 것보다 필요한 자원이 적다.

### RAG

RAG(Retrieval-Augmented Generation)는 질문과 관련된 내부 문서를 먼저 검색한 뒤, 검색한 내용을 Base Model에 함께 제공해 답변하게 하는 방식이다. 모델이 회사 정보를 전부 외우는 것이 아니라 필요한 순간에 찾아서 참고한다.

```text
사용자 질문
  → 관련 사내 문서 검색
  → 질문과 검색 결과를 LLM에 전달
  → 문서를 근거로 답변 생성
```

## 시작부터 만난 문제: Device가 CPU였다

처음 환경을 실행했을 때 `Device: cpu`가 표시되었다. GPU가 없는 상태에서도 실행은 가능하지만 Fine-tuning 시간이 크게 늘어날 수 있다.

![Colab 실행 환경에서 Device가 cpu로 표시된 화면]({{ '/assets/images/ai-nova-sllm/01-colab-device-cpu.png' | relative_url }})

이 문제를 통해 모델 코드만큼 실행 환경도 중요하다는 것을 느꼈다. Colab에서는 런타임 유형에서 GPU 가속기를 선택하고 세션을 다시 시작해야 한다. STM32 보드나 센서 실습에서 전원과 통신 상태부터 확인했던 것처럼, AI 실습도 먼저 하드웨어와 라이브러리 환경을 확인해야 했다.

## Base Model은 모르는 회사 정보를 추측했다

VPN과 GPU·CPU의 차이처럼 일반적인 질문에는 그럴듯하게 답했다. 그러나 GPU의 처리 속도를 구체적인 프레임 수로 단정하는 등 확인되지 않은 내용도 포함했다.

사내 Domain 질문에서는 문제가 더 분명했다.

- 실제 NOVA-GPU 표준 CUDA는 12.4였지만 Base Model은 10.2라고 답했다.
- NOVA-Drive에서 삭제한 파일은 휴지통에서 30일 동안 복구할 수 있지만, 모델은 다른 복구 절차를 만들어 냈다.

![Base Model이 사내 CUDA 버전과 파일 복구 정책을 잘못 답한 화면]({{ '/assets/images/ai-nova-sllm/02-base-model-domain.png' | relative_url }})

Base Model은 AI-NOVA라는 이름과 질문에 포함된 단어를 보고 일반적인 VPN·GPU·파일 복구 지식을 회사 규칙처럼 이어 붙였다. 문장은 자연스러웠지만 정답은 아니었다. 센서 고장진단에서도 정상처럼 보이는 파형이 실제 고장을 숨길 수 있듯, LLM 답변도 표현만 보고 믿기보다 기준 데이터와 비교해야 한다고 느꼈다.

## Fine-tuning은 완료됐지만 정답을 학습하지 못했다

8개의 Q&A를 5 epoch, 10 step으로 학습했다. Training loss는 약 2.9432에서 2.4 수준으로 낮아졌고 LoRA adapter도 저장되었다.

![Fine-tuning 진행 과정과 training loss]({{ '/assets/images/ai-nova-sllm/03-finetuning-loss.png' | relative_url }})

학습 로그만 보면 정상적으로 끝난 것처럼 보인다. 그러나 같은 Domain 질문을 다시 입력한 결과는 기대와 달랐다.

- CUDA 질문에 여전히 10.2라고 답했다.
- NOVA-Drive 복구 정책도 Base Model과 비슷하게 잘못 설명했다.
- 여러 규칙을 조합하는 질문에서는 답변이 길어졌지만 문장이 중간에 끊기고 핵심 정보가 빠졌다.

![Fine-tuned Model의 Domain 질문 답변]({{ '/assets/images/ai-nova-sllm/04-finetuned-domain.png' | relative_url }})

이번 결과로 학습이 완료됐다는 사실과 원하는 지식을 정확히 학습했다는 사실은 다르다는 것을 알게 되었다. 데이터가 8개뿐이라 기존 모델의 지식과 표현 습관을 충분히 바꾸지 못한 것으로 보인다. Loss 감소만으로 실제 업무 정확성을 판단하면 안 된다는 점도 확인했다.

## RAG는 내부 문서를 찾아 정답의 근거로 사용했다

RAG는 CUDA 질문에서 유사도 0.909인 내부 문서를 검색해 12.4라고 답했다. NOVA-Drive 질문에서는 유사도 0.860인 문서를 찾아 휴지통 보관 기간 30일을 반영했다.

![RAG 검색 결과와 Domain 질문 답변]({{ '/assets/images/ai-nova-sllm/05-rag-domain.png' | relative_url }})

모델을 다시 학습하지 않았는데도 회사 문서가 답변의 기준이 되었다. 사내 챗봇에 RAG를 사용한다는 것은 직원의 질문이 들어올 때 VPN 매뉴얼, 장애 대응 절차, 최신 규정 등을 검색하고 그 내용을 바탕으로 답하게 만든다는 뜻이다.

다만 RAG도 완벽하지 않았다. 검색 문서에는 없는 추가 복구 절차가 답변에 붙었고, 일반 VPN 질문에서는 `Alibaba Cloud`라는 근거 없는 표현도 나왔다. 검색 결과를 잘 찾는 것과 최종 답변이 검색 결과만 사용하도록 제한하는 것은 별개의 문제였다.

## 여러 문서를 연결하는 유형 C 질문

유형 C는 일반 지식과 여러 Domain 규칙을 함께 사용해야 하는 질문이다.

> 외부에서 NOVA-GPU 서버에 접속해 PyTorch 학습을 수행하려 한다. NOVA-VPN과 CUDA 환경을 고려하면 어떤 절차로 문제를 해결해야 하는가?

![유형 C 질문에 대한 Base Model, Fine-tuned Model, RAG 비교]({{ '/assets/images/ai-nova-sllm/06-type-c-comparison.png' | relative_url }})

세 방법은 다음과 같은 차이를 보였다.

| 방법 | 관찰한 결과 |
| --- | --- |
| Base Model | VPN과 CUDA의 일반 절차는 설명했지만 NOVA-ID, CUDA 12.4, 표준 Docker 이미지 같은 회사 규칙은 반영하지 못했다. |
| Fine-tuned Model | 절차형 답변을 만들었지만 핵심 정보가 빠졌고 마지막 문장이 끊겼다. |
| RAG | 외부 접속 문서와 PyTorch 환경 문서를 함께 검색해 `NOVA-VPN → NOVA-ID 인증 → CUDA 12.4 확인 → 표준 AI Docker 이미지 사용`의 흐름으로 조합했다. |

유형 C는 한 문서의 정답을 그대로 찾는 문제가 아니었다. 여러 문서를 빠짐없이 검색하고 서로 모순되지 않게 조합해야 했다. IMU 고장진단에서 센서 하나의 값만 보지 않고 여러 신호와 운용 조건을 함께 판단했던 경험과 비슷하게 느껴졌다.

## Domain 정보가 바뀌자 차이가 더 분명해졌다

마지막으로 표준 CUDA 정보를 12.4에서 13.0으로 변경했다.

![CUDA 13.0으로 변경한 뒤 RAG와 기존 Fine-tuned Model의 답변]({{ '/assets/images/ai-nova-sllm/07-domain-update.png' | relative_url }})

RAG는 검색 문서를 바꾸자 즉시 CUDA 13.0을 답했다. 반면 기존 Fine-tuned Model은 새 정보를 알 수 없었고, 오히려 TensorFlow 2.0이라는 관계없는 내용을 생성했다.

회사 지식은 보안 정책, 서버 버전, 담당 부서처럼 자주 바뀐다. RAG는 데이터베이스나 문서를 수정하면 바로 최신 내용을 검색할 수 있다. Fine-tuning은 데이터 정리, 재학습, 검증, 배포가 다시 필요하므로 최신성 유지 비용이 더 크다.

## 실제 기업에서는 무엇을 선택할까

이번 실습 결과를 기준으로 다음처럼 구분할 수 있었다.

### RAG가 적합한 경우

- 사내 IT Helpdesk와 장애 대응 매뉴얼
- 보안 규정, 서버 버전, 제품 사양처럼 자주 바뀌는 정보
- 답변의 출처와 근거를 사용자에게 보여 줘야 하는 업무
- 이미 문서나 데이터베이스에 지식이 정리되어 있는 경우

### Fine-tuning을 고려할 수 있는 경우

- 회사 특유의 말투나 용어를 일관되게 사용해야 하는 경우
- 상담 분류, 출력 형식, 반복되는 응답 패턴을 안정화할 때
- 충분한 고품질 학습 데이터와 재학습·검증 비용을 확보한 경우

실제 서비스에서는 둘 중 하나만 선택하기보다 Fine-tuning으로 답변 스타일과 업무 형식을 맞추고, RAG로 최신 사실과 근거를 공급하는 혼합 방식이 현실적이라고 생각한다.

최근 배우고 있는 Docker, API, 데이터베이스, Vue, JavaScript, 서버 개념과 연결하면 전체 구조도 조금 더 구체적으로 보였다. 내부 문서를 데이터베이스에서 검색하고, API로 LLM에 전달하며, Docker로 동일한 실행 환경을 배포하는 흐름이 실제 기업용 AI 서비스에 가깝다.

## 마무리

이번 AI-NOVA Helpdesk 실습에서는 RAG가 Domain 답변의 정확성과 정보 변경 대응에서 가장 분명한 장점을 보였다. 그렇다고 Fine-tuning이 필요 없는 것은 아니다. 이번처럼 8개의 데이터로 사실을 주입하는 용도보다, 충분한 데이터가 있을 때 응답 스타일과 업무 형식을 안정화하는 용도로 이해하는 편이 맞았다.

무엇보다 자연스러운 문장이 정확한 답변을 의미하지 않는다는 점이 기억에 남았다. 앞으로 LLM 결과를 볼 때는 모델의 말투보다 어떤 데이터를 근거로 답했는지, 그 데이터가 최신인지, 답변에 근거 없는 내용이 추가되지 않았는지를 먼저 확인하려 한다.
