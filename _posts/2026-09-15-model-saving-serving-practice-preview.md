머신러닝 모델을 학습하고 정확도를 확인했다고 해서 실제 서비스가 완성되는 것은 아니다. 사용자가 모델을 이용하려면 학습 결과를 파일로 저장하고, 별도의 서버에서 복원한 뒤, 외부 요청에 예측 결과를 반환할 수 있어야 한다.

이번 실습에서는 **모델 학습과 실제 서비스 사이의 연결 과정**을 직접 확인한다. 아직 실습 전이므로 이 글에서는 앞으로 실행할 내용과 확인할 포인트를 미리 정리한다.

## 이번 실습의 전체 흐름

전체 과정은 다음과 같다.

```text
데이터 준비
  → 모델 학습
  → 모델 파일 저장
  → 새로운 프로세스에서 복원
  → FastAPI 서버 실행
  → HTTP 요청으로 예측
  → 워커별 서버 성능 비교
```

핵심은 모델을 잘 학습하는 방법보다, 이미 학습된 모델을 **재사용 가능한 형태로 저장하고 서비스하는 방법**을 이해하는 것이다.

## 1. 프레임워크별 모델 저장과 복원

먼저 scikit-learn, PyTorch, Keras로 만든 모델을 각각 파일로 저장하고 다시 불러온다.

| 프레임워크 | 저장 형식 | 실습에서 확인할 내용 |
|---|---|---|
| scikit-learn | `pickle(.pkl)` | 저장한 Python 모델 객체를 새 프로세스에서 복원 |
| PyTorch | `TorchScript(.pt)` | 원래 모델 클래스 없이 추론 가능한지 확인 |
| Keras | `.keras` | 모델 구조와 가중치가 함께 복원되는지 확인 |

### scikit-learn과 pickle

Iris 데이터로 `RandomForestClassifier`를 학습하고 모델을 pickle 파일로 저장한다. 이후 새로운 Python 프로세스에서 파일을 불러와, 다시 학습하지 않고도 같은 정확도와 예측 결과가 나오는지 비교한다.

여기서 중요한 구분이 있다. 같은 시드와 데이터를 사용해 학습 과정을 반복하는 것이 **재현성**이라면, pickle 복원은 이미 완성된 모델의 상태를 그대로 되살리는 것이다. 즉, pickle이 재현성을 만들어 주는 것이 아니라 학습된 결과를 파일에 보존한다.

![scikit-learn 모델 학습 및 pickle 저장 예상 화면]({{ '/assets/images/model-serving-preview/01-sklearn-train-pickle.png' | relative_url }})

> pickle은 역직렬화 과정에서 코드를 실행할 수 있으므로 출처를 신뢰할 수 있는 파일만 불러와야 한다.

### PyTorch와 TorchScript

PyTorch 실습에서는 학습된 신경망을 TorchScript 형식의 `.pt` 파일로 저장한다. 일반적인 PyTorch 모델은 복원할 때 원래 클래스 정의가 필요할 수 있지만, TorchScript에는 실행 그래프와 가중치가 포함되어 모델 클래스 없이도 추론할 수 있다.

실습에서는 Eager 모드와 TorchScript 모델의 정확도를 비교하고, 별도의 추론 프로그램에 원래 모델 클래스가 없는지도 살펴볼 예정이다.

### Keras 모델 저장

Keras에서는 모델을 `.keras` 형식으로 저장한다. 저장된 파일을 새 프로그램에서 불러온 뒤 `model.summary()`를 실행해 입력층부터 출력층까지 모델 구조가 복원됐는지 확인한다.

세 프레임워크의 파일 형식은 다르지만 공통 원리는 같다.

> 학습된 모델의 구조와 상태를 저장하고, 별도의 프로세스에서 복원해 추론한다.

## 2. FastAPI로 예측 API 만들기

모델 저장과 복원을 확인한 다음에는 학습된 모델을 FastAPI 서버에 연결한다. 클라이언트가 꽃받침과 꽃잎의 길이·너비를 JSON으로 보내면, 서버가 붓꽃 품종과 클래스별 확률을 반환하는 방식이다.

예상 요청은 다음과 같다.

```json
{
  "sepal_length_cm": 5.1,
  "sepal_width_cm": 3.5,
  "petal_length_cm": 1.4,
  "petal_width_cm": 0.2
}
```

예상 응답은 다음과 같다.

```json
{
  "predicted_class": "setosa",
  "probabilities": {
    "setosa": 1.0,
    "versicolor": 0.0,
    "virginica": 0.0
  }
}
```

이를 통해 학습 스크립트 안에서만 사용하던 모델이 다른 애플리케이션에서도 호출할 수 있는 API로 바뀌는 과정을 확인한다.

## 3. 모델은 서버가 시작될 때 한 번만 로드한다

예측 요청이 들어올 때마다 모델 파일을 다시 읽으면 디스크 접근과 역직렬화가 반복된다. 모델이 크거나 요청이 많아질수록 큰 성능 문제가 될 수 있다.

이번 실습에서는 FastAPI의 `lifespan`을 이용해 서버 시작 시 모델을 한 번만 메모리에 올리고, 이후 모든 요청에서 같은 모델 객체를 재사용한다.

```text
서버 시작
  → 모델 파일 1회 로드
  → 메모리에 모델 보관
  → 여러 예측 요청에서 재사용
```

`/health`를 여러 번 호출하고 예측 요청을 보내더라도 서버의 `[startup]` 모델 로드 로그가 한 번만 나타나는지가 핵심 검증 포인트다.

![FastAPI 서버 시작과 health check 예상 화면]({{ '/assets/images/model-serving-preview/02-fastapi-health-check.png' | relative_url }})

## 4. 세 가지 입력으로 API 동작 확인

서버가 실행되면 setosa, versicolor, virginica에 해당하는 세 가지 측정값을 `/predict`에 보낸다. 각 요청의 `predicted_class`가 예상 품종과 일치하는지 확인한다.

이때 `latency_ms`는 컴퓨터 상태에 따라 달라질 수 있다. 첫 실습의 성공 기준은 지연시간의 절대값이 아니라 다음 두 가지다.

- 모델 로드 로그가 서버 시작 시 한 번만 출력되는가?
- 세 입력의 예측 클래스가 모두 예상 결과와 일치하는가?

![세 가지 붓꽃 품종 API 예측 예상 화면]({{ '/assets/images/model-serving-preview/03-fastapi-predict.png' | relative_url }})

## 5. 워커 수에 따른 성능 비교

API가 한 번 정상 동작하는 것과 많은 사용자의 요청을 효율적으로 처리하는 것은 다른 문제다. PyTorch와 FastAPI 실습에서는 Uvicorn 서버를 워커 1개와 4개로 각각 실행하고 부하 테스트 결과를 비교한다.

주요 측정 항목은 다음과 같다.

- 초당 처리 요청 수인 처리량(throughput)
- 요청 한 건의 평균 지연시간(latency)
- p50, p95, p99 지연시간
- 동시 요청 수에 따른 성능 변화
- 요청 실패 횟수

Python 프로세스는 CPU 연산에서 GIL의 영향을 받을 수 있다. 워커를 늘리면 독립된 여러 프로세스가 요청을 처리하므로 처리량이 증가할 가능성이 있다. 반면 워커마다 모델을 따로 메모리에 올리기 때문에 메모리 사용량도 함께 증가한다.

따라서 실습에서는 특정 성능 수치 자체보다 **워커 수가 처리량·지연시간·메모리에 어떤 방향으로 영향을 주는지**에 집중한다.

## 6. 기초 이후 확장되는 도구들

기본 모델 저장과 API 서빙을 익힌 뒤에는 운영 환경에서 사용되는 도구로 범위가 확장된다.

- Airflow: 학습과 서빙 작업 순서 자동화
- KServe: Kubernetes 기반 모델 배포와 오토스케일링
- Ray Serve: CPU·GPU 컴포넌트의 분산 서빙과 독립 확장
- vLLM: 대규모 언어 모델의 고성능 서빙
- Kubeflow: 전처리·학습·평가·배포 파이프라인 구성
- MLflow: 실험, 모델 버전 및 레지스트리 관리
- LGTM: 로그·메트릭·트레이스 관측
- LangSmith: LLM 실행 추적과 평가
- AIOps: 이상 탐지, 근본 원인 분석과 조치 자동화

FastAPI는 단순한 모델을 빠르게 API로 만들 때 적합하고, KServe나 Kubeflow는 여러 팀과 모델을 Kubernetes 환경에서 표준화할 때 유용하다. 즉, 모든 도구를 사용하는 것이 목표가 아니라 운영 규모와 목적에 맞는 도구를 선택하는 것이 중요하다.

## 실습 전 체크리스트

실습 환경은 Apple Silicon 기반 macOS, Docker Desktop, Python 3.11과 `uv`를 기준으로 한다. 시작 전에는 다음 항목을 확인할 예정이다.

- Docker Desktop이 정상적으로 실행되는가?
- `uv`로 Python 3.11 가상환경을 만들 수 있는가?
- 실습 서버가 사용할 8331·8341 포트가 비어 있는가?
- scikit-learn, NumPy, FastAPI, Uvicorn을 불러올 수 있는가?
- PyTorch와 TensorFlow 설치에 필요한 저장 공간이 충분한가?

## 이번 실습에서 얻고 싶은 것

이번 실습을 마치면 다음 질문에 답할 수 있을 것으로 기대한다.

1. 학습된 모델은 어떤 정보를 파일에 저장하는가?
2. 저장한 모델을 재학습 없이 어떻게 복원하는가?
3. 모델을 FastAPI와 연결해 어떻게 외부에 제공하는가?
4. 모델을 요청마다 로드하면 왜 비효율적인가?
5. 워커 수는 서버의 처리량과 메모리에 어떤 영향을 주는가?
6. 모델의 예측 정확도와 서버의 운영 성능은 어떻게 다른가?

## 마무리

이번 실습의 핵심 질문은 하나다.

> 학습이 끝난 모델을 어떻게 저장하고, 다른 프로그램과 사용자가 안정적으로 이용할 수 있게 만들 것인가?

모델 개발 단계에서는 정확도가 가장 중요해 보이지만, 실제 서비스에서는 저장 형식, 로딩 시점, API 구조, 동시 요청 처리, 지연시간, 버전 관리와 모니터링도 함께 고려해야 한다.

이번 프리뷰에 이어 다음 글에서는 scikit-learn 모델을 실제로 학습해 pickle로 저장하고, 별도의 프로세스에서 복원한 결과를 정리해 볼 예정이다.
