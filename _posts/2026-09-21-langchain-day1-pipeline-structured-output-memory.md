LangChain 첫 실습에서는 기본 파이프라인, 구조화 출력, 대화 메모리를 차례로 익히고, 마지막에는 세 기능을 결합한 FAQ 챗봇을 실행했다.

처음에는 LangChain이 ChatGPT와 별도로 존재하는 또 다른 AI 모델이라고 생각했다. 실습을 진행하면서 LangChain은 모델 자체가 아니라 **LLM과 프롬프트, 출력 처리, 대화 기록, 외부 기능을 연결하는 조립 도구**라는 점을 이해했다.

이번 실습을 한 줄로 정리하면 다음과 같다.

```text
고객 문의
→ 정해진 항목으로 분류
→ 긴급도에 따라 처리 경로 선택
→ 사용자별 대화 맥락 유지
→ LangSmith에서 실행 과정 검증
```

## LangChain이 필요한 이유

LLM에 질문하고 답변을 받는 것만으로는 실제 서비스를 만들기 어렵다. 고객 상담 서비스를 예로 들면 단순한 문장 생성 외에도 다음 기능이 필요하다.

- 고객의 문의 유형과 긴급도를 판별한다.
- 결과를 데이터베이스나 다른 프로그램에서 사용할 수 있는 형태로 만든다.
- 이전 대화를 기억해 후속 질문의 맥락을 이해한다.
- 긴급한 문의는 일반 답변 대신 담당자에게 전달한다.
- 각 실행 과정이 의도대로 동작했는지 기록을 확인한다.

LangChain은 이러한 기능을 여러 조립 블록으로 나눠 연결할 수 있게 해준다.

LLM이 답변을 만드는 엔진이라면 LangChain은 엔진과 다른 부품을 연결하는 구조에 가깝다. LangSmith는 연결된 과정의 입력, 출력, 오류와 실행 시간을 확인하는 기록 장치다.

## 기본 파이프라인에서 배운 점

첫 번째 실습에서는 프롬프트, 모델, 파서가 하나의 흐름으로 연결되는 과정을 확인했다.

처음에는 세 요소가 왜 따로 필요한지 바로 이해되지 않았다. 실행 흐름을 나눠 보면서 프롬프트는 AI에게 전달할 질문을 만들고, 모델은 답변을 생성하며, 파서는 모델의 결과에서 서비스가 사용할 내용을 꺼내는 역할이라는 것을 알게 됐다.

```text
사용자 입력
→ 모델에 전달할 질문 구성
→ 모델이 답변 생성
→ 애플리케이션에서 사용할 결과 추출
```

이를 통해 LLM 호출이 단순히 질문을 보내는 한 번의 작업이 아니라, 입력을 준비하고 답변을 생성한 뒤 결과를 처리하는 단계로 구성된다는 점을 배웠다.

이 구조를 사용하면 프롬프트나 모델을 변경하더라도 전체 프로그램을 다시 만들 필요가 없다. 필요한 부품만 교체하면서 동일한 실행 흐름을 재사용할 수 있다는 점이 LangChain의 장점이었다.

## 구조화 출력에서 배운 점

일반적인 LLM은 사람이 읽기 좋은 자유로운 문장으로 답한다. 하지만 프로그램은 문장의 의미를 매번 다시 해석하기 어렵다.

구조화 출력 실습에서는 고객 문의를 다음 세 항목으로 나누었다.

- 문의 종류
- 긴급도
- 문의 내용 요약

환불 요청이 3일 동안 처리되지 않았다는 문의를 입력하자 모델은 환불 관련 문의로 분류하고 긴급도를 높음으로 판단했다. 이 결과는 사람이 읽기 위한 설명문이 아니라 프로그램이 바로 사용할 수 있는 데이터였다.

덕분에 다음과 같은 후속 처리가 가능해진다.

```text
긴급도 높음
→ 담당자에게 전달

긴급도 보통 또는 낮음
→ FAQ 자동 답변
```

구조화 결과를 JSON으로 변환하는 과정도 확인했다. JSON 형태라면 결과를 데이터베이스에 저장하거나 REST API를 통해 다른 서비스에 전달할 수 있다.

실습 결과에서 한계도 발견했다. 모델이 정해진 필드는 잘 지켰지만 로그인 문의를 기타로 분류하거나, 환불과 결제 문제를 고객 서비스라는 넓은 범주로 분류하기도 했다. 실제 서비스에서는 문의 유형을 미리 정한 목록으로 제한해야 결과를 일관되게 유지할 수 있다는 점을 배웠다.

## 대화 메모리에서 배운 점

LLM이 이전 대화를 원래부터 기억한다고 생각하기 쉽지만 각각의 모델 호출은 기본적으로 독립적이다.

대화 메모리 실습에서는 한 세션에서 이름을 알려준 뒤 다시 이름을 질문했다. 모델은 앞에서 알려준 이름을 정확히 답했다. 이후 다른 세션에는 다른 이름을 알려주고 원래 세션으로 돌아가 질문했을 때, 두 사용자의 정보가 섞이지 않는 것도 확인했다.

```text
user-a → 철수의 대화 기록
user-b → 영희의 대화 기록
```

이를 통해 세션 ID는 사용자별 대화방 번호와 같은 역할을 한다는 것을 이해했다.

대화 메모리가 모델을 다시 학습시키는 기능이 아니라는 점도 중요했다. 과거 메시지를 저장해 두었다가 다음 질문을 보낼 때 함께 전달하기 때문에 모델이 기억하는 것처럼 보이는 것이다.

이번 실습에서 사용한 메모리는 프로그램이 종료되면 사라지는 방식이었다. 실제 서비스에서 장기적으로 대화를 보관하려면 데이터베이스나 별도의 영구 저장 기능이 필요하다.

## FAQ 챗봇 종합실습

마지막에는 기본 파이프라인, 구조화 출력, 대화 메모리를 결합한 FAQ 챗봇을 실행했다.

일반적인 배송 문의는 배송 카테고리와 중간 긴급도로 분류되어 FAQ 답변 경로로 처리됐다. 같은 사용자가 이어서 앱에서도 배송 조회가 가능한지 질문하자 챗봇은 앞선 대화가 배송 조회에 관한 내용이었다는 사실을 반영해 답했다.

환불 요청이 3일 동안 처리되지 않았다는 문의는 높은 긴급도로 분류됐다. 이 문의는 일반 FAQ 답변이 아니라 담당자 확인이 필요한 경로로 전달됐다. 이후 같은 사용자가 앞에서 문의한 내용을 요약해 달라고 요청하자 챗봇은 환불 요청과 무응답 상태를 정확하게 설명했다.

```text
배송 문의
→ 배송 / 중간 긴급도
→ FAQ 답변
→ 후속 질문에서 배송 조회 맥락 유지

환불 무응답 문의
→ 환불 / 높은 긴급도
→ 담당자 확인 경로
→ 후속 질문에서 환불 맥락 유지
```

최종적으로 사용자별 메시지가 각각 분리돼 저장된 것도 확인했다. 이 실습을 통해 세 가지 패턴이 서로 독립된 기능이 아니라 하나의 서비스 안에서 순서대로 연결된다는 점을 이해했다.

## LangSmith로 실행 과정 확인하기

최종 답변만 확인하면 내부에서 어떤 값이 만들어졌는지 알기 어렵다. LangSmith를 연결한 뒤 환불 문의의 실행 기록을 확인했다.

입력에는 환불 요청이 3일째 처리되지 않았다는 문장이 전달됐고, 출력에는 환불 카테고리, 높은 긴급도와 문의 요약이 기록됐다. 이 결과가 긴급 문의 분기의 근거가 됐다.

LangSmith를 통해 다음 항목을 확인할 수 있었다.

- 실제 모델에 전달된 입력
- 구조화된 출력값
- 실행 단계와 순서
- 각 단계의 실행 시간
- 오류가 발생한 위치

이를 통해 AI 서비스에서는 최종 문장뿐 아니라 중간 단계의 입력과 출력도 검증해야 한다는 점을 배웠다.

## 실습 중 어려웠던 점

### 가상환경은 켜졌는데 다른 Python이 실행됐다

**상황**

가상환경을 활성화했는데도 컴퓨터에 설치된 공용 Python이 실행됐다.

**원인과 해결**

터미널의 Python 명령에 설정된 별칭이 가상환경의 Python보다 먼저 적용되고 있었다. 별칭을 해제하고 실행 경로가 실습용 가상환경을 가리키는지 확인해 해결했다.

> **배운 점:** 터미널에 가상환경 이름이 표시되는 것만 믿지 말고, 실제로 실행되는 Python의 경로까지 확인해야 한다.

---

### VS Code에 새 커널이 나타나지 않았다

**상황**

새로 만든 가상환경이 VS Code의 Jupyter 커널 목록에 나타나지 않았다. 커널을 등록한 뒤에도 기존 목록만 보였다.

**원인과 해결**

VS Code 창을 다시 불러오자 Python과 Jupyter 확장 기능이 커널 목록을 다시 검색했고 실습용 커널을 선택할 수 있었다.

> **배운 점:** 가상환경은 패키지를 분리하는 공간이고, Jupyter 커널은 노트북이 실제로 사용할 Python 환경을 선택하는 장치다.

---

### 환경변수 파일을 찾지 못했다

**상황**

노트북과 API 키가 저장된 환경변수 파일이 서로 다른 폴더에 있어 키를 불러오지 못했다.

**원인과 해결**

노트북을 프로젝트 폴더로 이동하자 환경변수 파일을 정상적으로 찾았다.

> **배운 점:** 프로그램은 보통 현재 실행 위치를 기준으로 파일을 찾는다. 파일이 다른 위치에 있다면 정확한 경로를 지정해야 한다.

---

### 경고와 오류를 구분하기 어려웠다

**상황**

FAQ 챗봇을 실행하자 대화 메모리 기능이 향후 다른 방식으로 대체될 예정이라는 메시지가 나왔다. 처음에는 실행 실패라고 생각했지만 결과는 정상적으로 생성됐다.

**원인과 확인 결과**

오류는 프로그램 실행을 중단시키지만, 경고는 현재 기능이 작동하더라도 앞으로 변경될 수 있다는 정보를 제공한다. 메시지의 종류를 구분하고 실제 실행 결과를 함께 확인해야 한다는 점을 알게 됐다.

> **배운 점:** 경고가 보인다고 무조건 실패한 것은 아니다. 메시지 종류와 실제 실행 결과를 함께 확인해야 한다.

---

### LangSmith를 켰지만 기록이 나타나지 않았다

**상황**

추적 기능을 켰는데도 LangSmith에 실행 기록이 나타나지 않았다.

**원인과 해결**

환경변수와 프로젝트 이름을 확인하고 간단한 연결 테스트를 실행했다. 기록 전송이 완료된 뒤 실제 Trace를 확인할 수 있었다.

> **배운 점:** 설정값이 존재하는 것과 외부 서비스에 데이터가 실제로 전송되는 것은 별개의 문제이므로 각각 확인해야 한다.

## 어디에 활용할 수 있을까

이번에 배운 기본 파이프라인, 구조화 출력, 대화 메모리는 고객 상담뿐 아니라 자연어를 입력받는 대부분의 AI 서비스에 활용할 수 있다.

### 고객 문의 자동 분류

고객센터에는 배송, 결제, 환불, 로그인 등 다양한 문의가 들어온다. 상담원이 모든 문의를 읽고 담당 부서를 지정하는 대신 AI가 문의 종류와 긴급도를 먼저 판단할 수 있다.

```text
고객 문의
→ 문의 유형과 긴급도 분석
→ 담당 부서 자동 지정
→ 긴급 문의 우선 처리
```

상담원은 반복적인 분류 업무를 줄이고 실제 문제 해결에 집중할 수 있다.

### 사내 업무 요청 처리

회사 구성원이 자연어로 작성한 요청을 정해진 업무 데이터로 바꿀 수 있다. 회의 요청에서 날짜, 시간, 장소와 참석 대상을 추출해 사내 시스템이 처리할 수 있는 형식으로 변환하는 것이 한 예다.

이후 Tool Binding을 연결하면 캘린더 등록이나 알림 전송 같은 실제 작업으로 확장할 수 있다.

### 이메일과 민원 자동 정리

여러 사람이 서로 다른 형식으로 작성한 이메일이나 민원을 공통된 양식으로 정리할 수 있다.

```text
긴 이메일
→ 핵심 내용 요약
→ 요청 사항 추출
→ 중요도 판단
→ 담당자 지정
```

구조화 출력으로 결과 형식을 통일하면 데이터베이스 저장과 통계 분석도 쉬워진다.

### 리뷰와 고객 반응 분석

상품 리뷰나 SNS 게시물을 긍정, 중립, 부정으로 분류하고 주요 불만을 정리할 수 있다. 부정 리뷰만 담당자에게 전달하거나 반복적으로 발생하는 배송, 가격, 품질 문제를 빠르게 발견하는 데 활용할 수 있다.

### 개인화된 상담과 교육 서비스

대화 메모리를 사용하면 사용자가 같은 정보를 반복해서 입력하지 않아도 된다. 고객이 앞에서 제공한 주문번호를 후속 배송 질문에 활용하거나, 학생이 이전에 어려워했던 개념을 기억해 난이도를 조절하는 AI 튜터를 만들 수 있다.

다만 사용자별 세션을 정확히 분리하지 않으면 다른 사람의 정보가 섞일 수 있으므로 주의해야 한다.

### 사내 문서 검색 챗봇으로 확장

현재 실습은 FAQ 답변을 모델의 지식으로 생성했지만, 이후 RAG를 연결하면 회사 규정이나 매뉴얼을 검색해 근거와 함께 답하게 만들 수 있다.

```text
직원 질문
→ 관련 사내 문서 검색
→ 검색 결과를 근거로 답변
→ 참고한 문서와 출처 표시
```

휴가 규정, 경비 처리 방법, 보안 지침 등을 알려주는 사내 챗봇으로 발전시킬 수 있다.

### 외부 시스템과 연결

Tool Binding을 추가하면 챗봇이 답변만 하는 것을 넘어 주문 조회, 캘린더 등록, 날씨 조회, 이메일 전송처럼 실제 시스템의 기능을 사용할 수 있다.

중요한 작업은 모델이 선택한 값을 그대로 실행하지 않고 권한과 입력값을 검증하거나 사용자의 최종 승인을 받도록 설계해야 한다.

## 만들어 볼 수 있는 서비스

이번 실습 내용을 기반으로 다음과 같은 작은 프로젝트를 만들 수 있다.

- 사용자별 대화를 기억하는 FAQ 챗봇
- 긴급 문의를 자동으로 탐지하는 고객센터 도우미
- 리뷰를 긍정·부정으로 분류하는 모니터링 도구
- 이메일을 요약하고 담당 부서를 추천하는 시스템
- 사내 규정 문서를 검색하는 업무 챗봇
- 주문 상태를 조회하고 상담원에게 전달하는 쇼핑몰 챗봇

처음부터 복잡한 Agent를 만들 필요는 없다. 기본 파이프라인으로 작은 기능을 만든 뒤 구조화 출력, 메모리, Tool과 RAG를 필요한 만큼 추가하는 방식이 더 이해하기 쉽고 안전하다.

## 실습을 마치며

이번 실습에서 가장 크게 바뀐 점은 LLM을 단순한 대화 상대가 아니라 서비스의 한 부품으로 보기 시작했다는 것이다.

기본 파이프라인은 LLM 호출 과정을 재사용 가능한 흐름으로 만들었다. 구조화 출력은 자연어 답변을 프로그램이 처리할 수 있는 데이터로 바꿨다. 대화 메모리는 사용자별 문맥을 유지했다. 세 기능을 결합하자 일반 문의와 긴급 문의를 구분하고 이전 대화까지 기억하는 FAQ 챗봇을 만들 수 있었다.

또한 정상적인 답변이 나온다는 사실만으로는 충분하지 않다는 점도 알게 됐다. 실제 서비스에서는 Python 환경, 데이터 형식, 사용자별 세션 분리, 분류 기준과 실행 기록까지 함께 관리해야 한다.

앞으로 Tool Binding, Retry, Fallback, RAG와 Agent를 추가하면 LLM이 답변만 생성하는 수준을 넘어 외부 시스템을 조회하고 실패에 대응하며 필요한 행동을 선택하는 서비스로 확장할 수 있을 것이다.
