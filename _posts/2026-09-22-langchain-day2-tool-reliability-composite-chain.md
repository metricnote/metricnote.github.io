LangChain 두 번째 실습에서는 LLM이 문장을 생성하는 수준을 넘어 외부 기능을 선택하고, 실패에 대응하며, 여러 분석 결과를 하나의 업무 흐름으로 연결하는 방법을 익혔다.

Day 1에서는 입력을 분류하고 사용자별 대화를 기억하는 FAQ 챗봇을 만들었다. Day 2에서는 여기에 Tool Binding, Retry와 Fallback, 병렬 분석과 조건 분기를 추가해 고객 댓글을 처리하는 자동화 흐름으로 확장했다.

이번 실습을 한 줄로 정리하면 다음과 같다.

```text
고객 댓글
→ 요약·감정·키워드 병렬 분석
→ 긍정 또는 부정 경로 선택
→ 필요한 경우 외부 정보 조회
→ 고객 답변 또는 담당자용 메시지 생성
→ LangSmith에서 전체 실행 경로 확인
```

<br>

## 답변하는 AI에서 행동하는 AI로

LLM은 문장을 이해하고 생성하는 데 강하지만, 그것만으로 실제 주문 상태를 확인하거나 사내 시스템에 작업을 요청할 수는 없다. 모델이 알고 있는 내용과 회사 시스템이 보유한 현재 정보는 서로 다르기 때문이다.

예를 들어 고객이 배송 지연을 문의했을 때 모델이 일반적인 답변을 만드는 것만으로는 충분하지 않다. 현재 배송 상태를 조회하고, 고객의 주장과 시스템 기록이 다르면 자동으로 결론을 내리지 않고 담당자에게 전달해야 한다.

Day 2에서는 이 문제를 다음 세 가지 패턴으로 나누어 해결했다.

- **Tool Binding:** 자연어 요청에 맞는 외부 기능과 입력값을 선택한다.
- **Retry와 Fallback:** 일시적인 장애에 다시 시도하고, 계속 실패하면 대체 경로를 사용한다.
- **복합 Chain:** 독립적인 분석은 동시에 실행하고 결과에 따라 처리 경로를 나눈다.

세 패턴을 합치자 LLM이 모든 일을 직접 처리하는 구조가 아니라, 모델과 프로그램이 각자 잘하는 일을 나누는 구조가 만들어졌다.

<br>

## Tool Binding에서 배운 점

Tool Binding은 모델에게 사용할 수 있는 기능의 이름, 역할과 입력 형식을 알려주는 방식이다. 사용자가 자연어로 질문하면 모델은 어떤 기능이 필요한지 판단하고 해당 기능에 전달할 값을 만든다.

실습에서는 날씨처럼 외부 정보가 필요한 질문과 주문 상태를 확인해야 하는 질문을 구분했다. 단순한 감사 인사처럼 외부 기능이 필요하지 않은 입력에는 Tool 호출이 만들어지지 않는 것도 확인했다.

```text
사용자 요청
→ 모델이 의도 파악
→ 필요한 Tool과 입력값 선택
→ 애플리케이션이 입력값 검증
→ Tool 실행
→ 결과를 이용해 답변 생성
```

처음에는 Tool을 모델에 연결하면 모델이 함수 실행까지 모두 처리한다고 생각했다. 하지만 실제로 Tool Binding은 **호출할 기능과 입력값을 제안하는 단계**에 가깝다. 제안된 값을 확인하고 실제 기능을 실행하는 책임은 애플리케이션에 있다.

이 구분은 안전 측면에서도 중요했다. 조회 기능은 비교적 위험이 작지만, 결제 취소나 데이터 삭제처럼 외부 상태를 바꾸는 작업은 모델의 판단만으로 바로 실행하면 안 된다. 입력값, 권한과 사용자 의사를 프로그램에서 다시 확인해야 한다.

<br>

## Retry와 Fallback에서 배운 점

AI 서비스는 모델 API나 외부 시스템에 의존하기 때문에 일시적인 네트워크 문제나 응답 지연이 발생할 수 있다. 한 번의 실패로 전체 서비스가 멈추지 않게 하려면 실패의 종류에 따라 대응 방법을 나누어야 한다.

### Retry

Retry는 같은 요청을 다시 시도하는 방식이다. 잠깐 발생한 시간 초과나 일시적인 연결 문제처럼 다시 시도하면 성공할 가능성이 있는 오류에 적합하다.

실습에서는 앞의 시도가 실패한 뒤 정해진 횟수 안에서 다시 실행되고, 이후 성공하는 흐름을 확인했다.

### Fallback

Fallback은 기존 경로가 계속 실패할 때 다른 모델이나 대체 기능으로 전환하는 방식이다. 같은 요청을 반복해도 해결되지 않는 문제라면 재시도만 계속하는 것보다 다른 경로를 선택하는 편이 낫다.

```text
Primary 실행
→ 일시적 실패라면 Retry
→ 정해진 횟수만큼 실패
→ Backup 경로로 Fallback
```

두 패턴의 차이를 구분하는 것이 중요했다. Retry는 **같은 방법을 다시 시도**하는 것이고, Fallback은 **다른 방법으로 전환**하는 것이다.

또한 무조건 많이 재시도하는 것이 좋은 설계는 아니다. 재시도 횟수가 늘어나면 응답 시간과 비용도 증가한다. 실제 서비스에서는 오류 유형, 최대 시도 횟수, 대기 시간과 최종 실패 처리 방식을 함께 정해야 한다.

<br>

## 병렬 분석과 복합 Chain에서 배운 점

고객 댓글 하나를 처리하려면 내용 요약, 감정 판단과 핵심 키워드 추출이 필요할 수 있다. 세 작업은 같은 댓글을 사용하지만 서로의 결과를 기다릴 필요가 없다.

순차 실행에서는 첫 번째 분석이 끝난 뒤 두 번째 분석을 시작한다. 반면 병렬 실행에서는 독립적인 작업을 동시에 시작할 수 있어 전체 대기 시간을 줄일 수 있다.

```text
고객 댓글
├─ 내용 요약
├─ 감정 판단
└─ 핵심 키워드 추출
        ↓
   결과를 하나로 결합
        ↓
   조건에 따라 경로 선택
```

분석 결과가 긍정적이면 고객에게 감사 답변을 만들고, 부정적이면 담당자가 확인할 메시지를 생성하도록 분기했다. 주문 관련 정보가 포함된 경우에는 외부 조회 결과도 함께 반영했다.

여기서 중요한 점은 모든 흐름에 Agent가 필요한 것은 아니라는 사실이었다. 긍정과 부정을 나누는 기준이나 주문번호의 존재 여부처럼 조건이 명확하면 고정된 Chain과 조건 분기가 더 단순하고 예측 가능하다.

<br>

## 종합실습에서 확인한 실행 흐름

마지막에는 세 패턴을 고객 댓글 자동 처리 과정으로 연결했다.

배송 지연과 포장 문제를 함께 언급한 부정적인 댓글은 요약, 감정과 키워드가 각각 분석된 뒤 담당자 확인 경로로 이동했다. 주문 관련 정보가 있는 경우에는 현재 상태를 조회해 고객의 설명과 함께 담당자 메시지에 반영했다.

긍정적인 댓글은 불필요한 조회 없이 감사 답변 경로로 처리됐다. 이를 통해 같은 파이프라인이라도 입력의 성격에 따라 실행되는 단계가 달라질 수 있다는 점을 확인했다.

```text
긍정 댓글
→ 병렬 분석
→ 고객 감사 답변

부정 댓글
→ 병렬 분석
→ 주문 관련 정보 확인
→ 담당자 확인 메시지
```

형식이 일정한 값은 규칙으로 빠르게 처리하고, 띄어쓰기나 표현이 일정하지 않은 입력은 모델이 보완하도록 구성한 점도 인상적이었다. 모든 판단을 LLM에 맡기기보다 확실한 부분은 일반 프로그램이 처리하고 애매한 부분에만 모델을 사용하는 방식이 더 효율적이었다.

<br>

## LangSmith로 확인한 것

최종 결과만 보면 여러 분석이 정말 동시에 실행됐는지, 어떤 경로가 선택됐는지 알기 어렵다. LangSmith의 Trace에서 하나의 요청이 여러 하위 실행으로 나뉘고 다시 합쳐지는 과정을 확인했다.

![댓글별 입력과 최종 출력 목록](/assets/images/langchain-day2-2026-09-22/01-comment-input-output-list.png)

*제공된 실습 코드를 직접 실행한 뒤 LangSmith에서 확인한 댓글별 입력과 최종 출력 목록이다. 긍정 댓글과 부정 댓글이 서로 다른 형태의 답변으로 처리된 것을 확인할 수 있다.*

![병렬 분석과 Tool 호출 Trace](/assets/images/langchain-day2-2026-09-22/02-parallel-tool-trace.png)

*환불 및 배송 지연 문의를 직접 실행해 확인한 Trace다. 요약, 감정, 키워드 분석이 각각 실행된 뒤 분기 단계와 주문 상태 조회 Tool을 거쳐 최종 담당자용 메시지가 만들어졌다. 화면의 주문 정보와 고객 문장은 실제 개인정보가 아닌 실습용 예시 데이터다.*

확인한 항목은 다음과 같다.

- 요약, 감정과 키워드 분석이 각각 별도의 실행으로 기록됐는가
- 입력 댓글이 각 분석 단계에 정상적으로 전달됐는가
- 분석 결과에 따라 의도한 분기가 선택됐는가
- 외부 조회가 필요한 경우 Tool 이름과 입력값이 올바른가
- Tool 실행 결과가 최종 메시지에 반영됐는가
- 전체 실행 시간과 각 단계의 소요 시간은 얼마인가

이를 통해 LangSmith는 단순히 성공 여부를 보여주는 도구가 아니라, AI 애플리케이션의 판단 과정을 검증하는 관찰 도구라는 점을 이해했다.

<br>

## 실습 중 어려웠던 점

### Tool을 연결하면 자동으로 실행된다고 생각했다

**상황**

모델에 Tool을 알려주면 선택부터 실행까지 모두 자동으로 이루어진다고 생각했다.

**이해한 내용**

Tool Binding의 결과에는 호출할 Tool 이름과 입력값이 담긴다. 실제 실행은 애플리케이션이 담당하며, 실행 전에 입력값과 권한을 검증할 수 있다.

> **배운 점:** 모델은 행동을 제안하고 프로그램은 그 행동을 검증하고 실행한다. 두 역할을 분리해야 안전한 서비스를 만들 수 있다.

---

### Retry와 Fallback의 차이가 헷갈렸다

**상황**

두 기능 모두 실패에 대응한다는 점 때문에 언제 어떤 기능을 사용해야 하는지 구분하기 어려웠다.

**이해한 내용**

Retry는 동일한 요청을 다시 시도하며 일시적인 오류에 적합하다. Fallback은 다른 모델이나 대체 경로로 전환하며 반복해도 해결되지 않는 오류에 적합하다.

> **배운 점:** 오류가 다시 시도하면 해결될 문제인지, 다른 방법이 필요한 문제인지 먼저 판단해야 한다.

---

### 병렬 실행과 조건 분기를 한 흐름으로 이해하기 어려웠다

**상황**

한 댓글이 여러 분석기로 전달되고, 다시 하나의 결과로 합쳐진 뒤 처리 경로가 나뉘는 구조가 처음에는 복잡하게 느껴졌다.

**이해한 내용**

흐름을 분석 단계와 행동 단계로 나누자 이해하기 쉬워졌다. 먼저 독립적인 분석을 동시에 수행하고, 결과가 모인 뒤 감정과 주문 정보에 따라 다음 행동을 선택하는 구조였다.

> **배운 점:** 복합 파이프라인은 입력, 독립 분석, 결과 결합, 조건 분기와 최종 행동으로 나누어 보면 이해하기 쉽다.

---

### 형식이 맞는 값과 실제 근거가 있는 값을 구분해야 했다

**상황**

모델이 만들어 낸 값이 정해진 형식에는 맞아도 사용자의 원문이나 시스템 데이터에 실제로 존재한다고 보장할 수는 없었다.

**해결 방향**

외부 조회나 상태 변경에 사용할 값은 원문에서 확인됐는지 다시 검사하고, 조회 결과와 고객의 설명이 다르면 자동으로 결론 내리지 않고 담당자에게 전달하도록 설계했다.

> **배운 점:** 구조화 출력은 형식을 보장하지만 사실 여부까지 보장하지는 않는다. 중요한 값은 신뢰 가능한 데이터와 다시 비교해야 한다.

---

### 경고와 실제 오류를 구분해야 했다

**상황**

라이브러리 변경 예정이라는 경고가 출력돼 실행이 실패한 것으로 오해하기 쉬웠다.

**확인 결과**

경고가 있어도 결과가 정상적으로 생성되는 경우가 있었다. 반면 필요한 패키지가 없거나 실행 환경이 다르면 프로그램이 실제로 중단됐다.

> **배운 점:** 메시지 이름만 보고 판단하지 말고 프로그램이 중단됐는지, 결과가 생성됐는지와 실제 Trace를 함께 확인해야 한다.

## 이번 실습에서 가장 크게 배운 점

첫째, LLM은 모든 일을 직접 처리하는 존재가 아니라 여러 기능 중 필요한 행동을 선택하는 역할로 사용할 수 있다.

둘째, 모델의 판단은 그대로 신뢰하기보다 애플리케이션에서 검증해야 한다. 특히 외부 시스템을 조회하거나 상태를 변경하는 작업은 입력값과 권한을 확인하는 단계가 필요하다.

셋째, 실패는 예외적인 사건이 아니라 서비스 설계에 포함해야 하는 정상적인 상황이다. 일시적 실패에는 Retry를 적용하고, 지속적인 실패에는 Fallback을 준비해야 한다.

넷째, 서로 의존하지 않는 작업은 병렬로 실행할 수 있다. 다만 앞 단계의 결과가 필요한 작업까지 무조건 병렬로 만들면 안 된다.

마지막으로 결과 문장이 자연스럽다는 사실만으로 서비스가 제대로 동작했다고 판단할 수 없다. 어떤 분석이 실행됐고 어떤 Tool이 선택됐으며 실제 결과가 답변에 반영됐는지를 Trace로 확인해야 한다.

<br>

## 어디에 활용할 수 있을까

### 고객 리뷰 자동 처리

리뷰를 요약하고 감정과 주요 불만을 분석해 긍정 리뷰에는 감사 답변을 보내고, 부정 리뷰에는 담당자 확인 요청을 만들 수 있다. 배송이나 결제와 관련된 내용은 실제 시스템 조회 결과와 함께 전달할 수 있다.

### 고객센터 업무 분배

문의 내용을 분석해 담당 부서를 추천하고 긴급한 요청은 우선 처리할 수 있다. 외부 시스템이 일시적으로 응답하지 않을 때 재시도하거나 대체 안내를 제공하도록 구성할 수 있다.

### 이메일과 민원 분류

긴 문서를 요약하고 주제, 감정과 요청 사항을 동시에 추출한 뒤 담당자에게 전달할 수 있다. 반복되는 불만을 키워드별로 모아 서비스 개선 자료로 활용할 수도 있다.

### 장애 대응 자동화

외부 API가 일시적으로 실패하면 다시 시도하고, 계속 실패하면 다른 모델이나 저장된 정보로 전환할 수 있다. 모든 경로가 실패했을 때는 담당자에게 알리고 사용자에게 현재 상황을 안내하도록 만들 수 있다.

### 사내 업무 도우미

구성원의 자연어 요청을 이해해 필요한 사내 기능을 선택할 수 있다. 일정 조회, 문서 검색과 알림 전송처럼 서로 다른 기능을 조합할 수 있지만, 중요한 변경 작업에는 사용자 확인 단계를 추가해야 한다.

<br>

## Chain과 Agent 중 무엇을 선택해야 할까

Day 2 실습은 복잡해 보였지만 실행 규칙은 미리 정할 수 있었다. 분석할 항목, 분기 조건과 후속 행동이 정해져 있었기 때문에 Chain이 적합했다.

```text
순서와 조건을 미리 정할 수 있음
→ Chain

필요한 Tool과 반복 횟수를 실행 중에 판단해야 함
→ Agent
```

Agent는 유연하지만 실행 경로를 예측하기 어렵고 비용과 검증 부담이 커질 수 있다. 따라서 처음부터 모든 기능을 Agent로 만들기보다, 고정할 수 있는 작업은 Chain으로 구성하고 정말 동적인 판단이 필요한 부분에만 Agent를 사용하는 것이 적절하다.

<br>

## 실습을 마치며

Day 2에서는 LLM이 실제 시스템과 연결될 때 필요한 세 가지 요소를 배웠다. Tool Binding은 자연어 요청과 프로그램 기능을 연결했고, Retry와 Fallback은 외부 서비스의 실패에 대응했으며, 복합 Chain은 여러 분석과 조건 분기를 하나의 업무 흐름으로 묶었다.

가장 중요한 변화는 모델의 답변만 보는 것에서 실행 과정 전체를 보는 것으로 관점이 바뀐 것이다. 어떤 Tool을 선택했는지, 입력값은 올바른지, 실패했을 때 어떤 경로로 이동했는지까지 확인해야 서비스의 동작을 신뢰할 수 있다.

다음 단계에서는 사내 문서처럼 모델이 원래 알지 못하는 정보를 검색하는 RAG와, 질문에 따라 여러 Tool을 스스로 선택하는 Agent를 연결해 더 유연한 AI 서비스로 확장할 수 있을 것이다.
