> GitHub: [AI_Investment_project](https://github.com/jun-yeong1/AI_Investment_project)

## 프로젝트를 시작한 이유

이번 팀 프로젝트의 주제는 **AI 신약개발 스타트업의 투자 적격성을 평가하는 AI 에이전트**를 만드는 것이었다.

일반적인 챗봇처럼 질문에 답하는 것만으로는 부족했다. 투자 판단에는 기업의 기술력뿐만 아니라 경영진, 임상 단계, 규제, 시장성, 자금 조달, 특허와 소송 등 여러 요소가 함께 사용되기 때문이다. 또한 AI가 그럴듯한 내용을 만들어 내지 않도록, 모든 판단에는 확인 가능한 근거가 필요했다.

그래서 다음과 같은 목표를 세웠다.

- 공식 문서와 웹 자료에서 투자 판단에 필요한 근거를 찾는다.
- 여러 조사 에이전트가 역할을 나누어 기업을 평가한다.
- LLM은 근거를 해석하고, 실제 점수 계산은 Python 코드가 담당한다.
- 최종 판정과 사용한 근거를 PDF 투자 보고서로 만든다.

### 왜 AI 신약개발 분야를 선택했을까?

AI 신약개발은 단순한 기업 소개보다 **확인 가능한 사건**을 중심으로 평가하기 좋은 분야였다. 파이프라인의 임상 단계, FDA IND 효력 발생, 식약처 임상시험계획 승인, 희귀의약품 지정, 기술이전 계약처럼 공개 자료로 교차 확인할 수 있는 이정표가 있기 때문이다.

또한 규제 가이드라인, 산업 보고서, 임상 성공률 자료처럼 RAG에 사용할 수 있는 공신력 있는 문서가 존재했다. 이번 프로젝트에서는 스탠다임, 디어젠, 갤럭스, 닥터노아바이오텍 등 비상장·성장 단계의 국내 AI 신약개발 기업 4곳을 평가 대상으로 정했다.

다만 이 시스템의 목적은 기업가치를 계산하거나 투자를 자동으로 결정하는 것이 아니다. 공개 근거를 정리해 **후속 실사가 필요한 기업과 확인할 질문의 우선순위**를 제시하는 데 초점을 맞췄다.

## 전체 구조

프로젝트의 전체 흐름은 다음과 같다.

```text
후보 기업 선택
    ↓
기업 조사 ─────────┐
기술·파이프라인 조사 ─┤
                     ├→ 투자 판단 → 보고서 생성
규제 조사 ──────────┤
시장·사업화 조사 ────┘
    ↓
다음 후보 기업 평가
```

기업 조사와 기술 조사는 먼저 병렬로 진행한다. 기술 에이전트가 물질명, 적응증, 개발 단계와 같은 파이프라인 정보를 찾으면, 그 결과를 규제 에이전트와 시장 에이전트에 전달한다.

모든 조사가 끝난 후에만 투자 판단을 실행한다. 첫 번째 적격 기업이 발견되더라도 바로 종료하지 않고, 후보 4곳을 모두 평가하도록 설계했다. 그래야 여러 적격 기업을 비교할 수 있고, 적격 기업이 한 곳도 없을 때에도 각 기업의 탈락 사유와 재검토 조건을 제시할 수 있다.

![LangGraph 기반 투자 평가 에이전트의 전체 실행 흐름]({{ '/assets/images/rag-investment-team-project/01-langgraph-architecture.png' | relative_url }})

*그림 1. 후보 4곳을 순회하며 조사·판정·보고서 생성을 반복하는 LangGraph 실행 구조*

### LangGraph State에는 무엇을 저장했나?

그래프의 노드만 연결해서는 여러 기업을 순서대로 평가하기 어렵다. 따라서 실행 중 필요한 정보를 공유 State에 저장했다.

| State | 역할 |
| --- | --- |
| `candidates`, `current_idx` | 후보 4곳과 현재 평가 순서 관리 |
| `company` | 현재 조사 중인 기업 |
| `pipeline` | 물질명·적응증·개발 단계 목록 |
| `evidence` | 조사 에이전트가 찾은 근거와 출처 누적 |
| `scores`, `total`, `verdict` | 항목별 점수와 최종 판정 |
| `evaluations` | 기업별 평가 결과 누적 |
| `reports` | 생성된 기업별 보고서 목록 |

특히 `evaluations`와 `reports`를 누적하도록 만든 덕분에 한 기업이 적격 판정을 받아도 그래프를 종료하지 않고 다음 후보로 넘어갈 수 있었다.

## 1. 투자 판단을 위한 RAG 구축

RAG는 LLM이 자신의 기억에만 의존하지 않고, 외부 문서를 먼저 검색한 뒤 그 내용을 근거로 답하게 하는 방식이다.

이번 프로젝트에서는 규제·기술·시장 분야의 공식 보고서와 논문 **6종, 총 134쪽**을 검색 대상으로 사용했다.

### 문서 전처리

PDF에서 텍스트와 페이지 번호를 추출하기 위해 PyMuPDF를 사용했다. 하지만 표, 그래프, 이미지로 구성된 페이지는 일반적인 텍스트 추출만으로 내용을 읽기 어려웠다. 이런 페이지는 Vision LLM으로 전사하고, 원문 확인이 필요한 수치는 별도로 구분했다.

처리 흐름은 다음과 같다.

```text
PDF 수집
→ 페이지별 텍스트 추출
→ 표·이미지 페이지 Vision 전사
→ 텍스트 정제
→ 청크 분할
→ 임베딩
→ FAISS 인덱스 저장
```

여기서 청크는 긴 문서를 검색하기 좋은 작은 단위로 나눈 것이다. 임베딩은 각 청크의 의미를 숫자 벡터로 바꾸는 과정이며, FAISS는 질문과 의미가 가까운 벡터를 빠르게 찾아주는 검색 도구다.

### 검색 방식 실험

처음 설계할 때는 BM25 키워드 검색과 Dense 의미 검색을 결합한 하이브리드 검색을 고려했다. 하지만 설계와 실제 성능은 다를 수 있으므로, 한 가지 방식을 바로 선택하지 않고 실험으로 비교했다.

- 청킹 방식 5종
- 임베딩 모델 3종
- 검색 방식 3종
- 평가 질문 34개

실험 결과 최종 설정은 다음과 같았다.

| 항목 | 선택한 설정 |
| --- | --- |
| 청킹 | 500자, 50자 overlap |
| 임베딩 | `BAAI/bge-m3` |
| 검색 | FAISS Dense 검색 |
| Hit Rate@3 | **0.824** |
| MRR | **0.703** |

이번 평가셋에서는 FAISS 단독 검색이 BM25와 하이브리드 방식보다 좋은 결과를 보였다. 따라서 “하이브리드가 항상 더 좋을 것”이라고 가정하지 않고, 측정 결과에 따라 Dense 검색을 최종 설정으로 선택했다.

Hit Rate@3가 0.824라는 것은 정답 문서가 상위 3개 검색 결과 안에 포함된 비율이 약 82.4%라는 뜻이다. MRR은 정답이 검색 결과의 얼마나 앞쪽에 등장하는지를 나타낸다.

### 한 번 더 검증하는 Agentic RAG

FAISS가 유사한 청크를 찾았다고 해서 그 내용이 질문의 답을 직접 포함한다는 보장은 없다. 그래서 검색 결과를 LLM이 다시 확인하도록 했다.

```text
한국어·영어 검색 질문 생성
→ 문서 종류별 검색
→ FAISS 후보 검색
→ LLM 관련성 검사
→ 근거 부족 시 질문을 한 번 재작성
→ 최종 근거와 출처 반환
```

검색 결과에는 본문만 주는 것이 아니라 문서명, 페이지, 청크 ID, 유사도 점수도 함께 반환한다. 관련 근거를 찾지 못했을 때는 억지로 답을 만들지 않고 빈 결과를 반환하도록 했다.

RAG에서 답을 찾지 못하면 웹 검색으로 보강하지만, 검색 결과의 요약문을 바로 근거로 사용하지는 않았다. 검색으로 URL 후보를 찾은 뒤 원문 페이지를 열어 관련 문단, 발행일, 접근일을 확인해 저장했다. 즉, RAG와 웹 검색 모두 최종적으로는 “어디에서 확인한 내용인지”를 추적할 수 있도록 설계했다.

## 2. 역할을 나눈 조사 에이전트

한 에이전트가 모든 것을 조사하면 프롬프트가 복잡해지고, 어떤 근거가 어떤 판단에 사용됐는지 추적하기 어렵다. 이를 해결하기 위해 조사 영역별로 역할을 나눴다.

### Company Research Agent

경영진의 전문성, 최근 투자 유치, 자금난, 구조조정, 기업 평판 등을 조사한다. 검색 결과의 짧은 요약만 사용하는 것이 아니라 원문을 열어 관련 문단과 날짜를 확인한다.

### Technology & Pipeline Agent

AI 플랫폼의 기술 검증 수준과 신약 파이프라인을 조사한다. 물질명, 적응증, 개발 단계 등을 구조화된 형태로 정리하고, 이 결과를 규제 및 시장 에이전트에 전달한다.

### Regulation Agent

회사 이름만으로 검색하지 않고 파이프라인별 물질과 적응증을 기준으로 IND, 임상시험계획 승인, Clinical Hold, 특허, 소송, 해외 임상 여부를 확인한다.

### Market & Commercialization Agent

시장 규모, 경쟁 약물, 기술이전, 공동연구, 계약 해지, 플랫폼 차별성, 상장 가능성과 같은 사업화 및 투자금 회수 요소를 조사한다.

LangGraph에서는 이 에이전트들의 실행 순서, 병렬 처리, 결과 전달, 다음 후보로 이동하는 조건을 그래프로 구성했다. 공유 State에는 현재 기업, 파이프라인, 조사 근거, 평가 결과와 보고서 정보가 저장된다.

## 3. 근거와 점수를 분리한 Investment Judge

LLM에게 “이 기업에 투자해도 될까?”라고 바로 물으면 답변이 일관되지 않을 수 있다. 같은 정보라도 실행할 때마다 점수가 달라질 가능성도 있다.

그래서 LLM과 코드의 역할을 분리했다.

- **LLM:** 각 평가 기준에 해당하는 사실이 있는지 판단하고 근거 ID를 선택한다.
- **Python 코드:** 정해진 규칙에 따라 점수를 계산하고 최종 판정을 내린다.

평가에는 RFSM의 12개 위험요인을 참고했다. 경영진, 사업 단계, 기술, 규제, 제조, 시장, 경쟁, 자금 조달, 해외 진출, 평판, 소송, 투자금 회수 가능성을 살펴본다.

근거 상태도 다음 네 가지로 구분했다.

- 확인됨
- 기업 주장만 존재함
- 찾지 못함
- 서로 상충함

이 구분이 중요한 이유는 “검색에서 찾지 못했다”와 “그 사실이 존재하지 않는다”가 전혀 다른 의미이기 때문이다. 또한 같은 근거가 여러 평가 항목에 중복으로 가점을 주지 않도록 제한했다.

기술과 법률·정책은 필수 관문으로 사용했다. 전체 점수 기준은 `+5`이며, 기준의 임의성을 보완하기 위해 `+4`, `+6`으로 바꿨을 때 판정이 어떻게 달라지는지도 함께 보여준다. 결과는 적격, 보류, 부적격으로 나누며, 보류 기업에는 다시 검토하기 위한 조건을 제시한다.

최종 판정은 다음 순서로 이루어진다.

1. 스타트업 조건에 맞지 않거나 관문 항목에서 확인된 `-2` 근거가 있으면 부적격으로 판정한다.
2. 기술과 법률·정책 관문이 모두 `+1` 이상인지 확인한다.
3. 기업·팀, 기술·파이프라인, 규제, 시장·사업화의 네 조사 영역에 확인된 근거가 있는지 검사한다.
4. 위 조건을 만족하면서 합계가 `+5` 이상이면 적격, 그 외에는 보류로 판정한다.

여기서 `+5`는 외부에서 검증된 절대 투자 기준이 아니라 이번 프로젝트의 운영 기준이다. 그래서 보고서에는 `+4`, `+5`, `+6`을 각각 적용한 민감도 분석도 함께 제시했다.

![12개 위험요인별 Judge 평가 기준]({{ '/assets/images/rag-investment-team-project/03-judge-rubric.png' | relative_url }})

*그림 3. 확인된 부정·긍정 근거와 기업 주장 수준을 구분한 12개 위험요인 평가표*

## 4. 근거 기반 PDF 보고서 생성

마지막 단계에서는 조사 결과와 Judge 판정을 이용해 투자 보고서를 만든다.

- 적격 기업별 보고서 생성
- 적격 기업이 여러 곳이면 PDF 병합
- 적격 기업이 없으면 후보 4곳의 사유와 재검토 조건 비교
- 실제 사용한 출처만 참고문헌에 수록
- 부족하거나 상충하는 근거는 한계점으로 명시

특히 요약문을 먼저 상상해서 작성하는 대신, 본문을 모두 만든 후 최종 판정과 핵심 이유를 압축해 SUMMARY를 생성하도록 했다.

## 5. 실제 실행 결과

제출 결과물에서는 네 번째 평가 기업인 닥터노아바이오텍이 `적격`으로 판정됐다. 합계는 `+12`, 100점 환산 점수는 `75.0점`이었다. 기술 관문은 `+1`, 법률·정책 관문은 `+2`로 통과했고, 기업·팀, 기술·파이프라인, 규제, 시장·사업화의 네 영역에서도 근거가 확인됐다.

기준점을 `+4`, `+5`, `+6`으로 바꾼 민감도 분석에서도 판정은 모두 적격으로 유지됐다. 결과 PDF에는 최종 판정만 적지 않고 다음 내용도 함께 담았다.

- 판정에 사용한 핵심 근거
- 12개 항목별 점수와 근거 상태
- 관문 통과 여부와 판정 규칙
- 공개 자료에서 찾지 못한 정보
- 기업 주장에만 의존한 내용
- 실제로 인용한 원문 목록

예를 들어 결과물은 경영진 이력, 소송, 경쟁 자료처럼 확인하지 못한 정보와 자금 조달·제조·해외 진출처럼 기업 주장에 의존한 정보를 한계점으로 따로 기록했다. 좋은 근거만 보여주는 것이 아니라 **무엇을 아직 모르는지도 결과의 일부로 제공한 것**이다.

## 구현하면서 만난 문제

### 1. PDF라고 해서 모두 텍스트로 읽히지는 않았다

표와 이미지가 많은 보고서는 일반 파서만 사용하면 중요한 정보가 빠졌다. Vision 전사를 추가해 해결했지만, 출력이 지나치게 길어지는 경우가 있어 길이 제한과 캐시를 적용했다. 캐시 덕분에 같은 문서를 처리할 때 Vision API를 반복 호출하지 않아도 됐다.

### 2. 검색 방식은 이름보다 평가 결과가 중요했다

처음에는 BM25와 Dense를 결합하면 당연히 더 좋을 것이라고 생각했다. 그러나 실제 평가에서는 BGE-M3 임베딩과 FAISS를 사용한 Dense 검색이 더 높은 성능을 보였다. 이번 경험을 통해 검색 시스템은 익숙한 방식이나 복잡한 방식이 아니라, 실제 질문으로 평가한 결과를 기준으로 선택해야 한다는 점을 배웠다.

### 3. LLM에게 모든 판단을 맡기면 재현성이 떨어졌다

LLM은 문장을 해석하는 데는 강하지만, 엄격한 점수 계산과 규칙 적용까지 모두 맡기면 결과가 흔들릴 수 있다. 사실 판별은 LLM에 맡기고 계산과 분기는 코드로 고정하면서 결과를 더 설명 가능하게 만들 수 있었다.

### 4. 여러 사람이 만든 코드를 합치는 것도 개발의 일부였다

RAG, 조사 에이전트, Judge, 보고서가 서로 다른 모듈로 개발됐기 때문에 인터페이스를 맞추는 작업이 중요했다. Git 브랜치와 Pull Request를 사용해 기능을 통합했고, 병합 과정에서 폴더 구조, 타입, README, 의존성을 계속 수정했다.

## 프로젝트 결과

이번 팀 프로젝트에서는 아이디어 수준의 설계를 실제로 실행 가능한 파이프라인으로 연결했다.

- 공식 문서 기반 RAG 데이터와 FAISS 인덱스 구축
- 검색 평가셋을 이용한 설정 비교 및 최종 검색기 선택
- LangGraph 기반 멀티 에이전트 실행 흐름 구현
- 12개 위험요인 기반 Judge와 결정론적 채점 구현
- 근거 상태와 출처를 포함한 평가 구조 설계
- 투자 결과 PDF 생성 및 적격 기업이 없는 경우의 보고서 처리
- 실제 후보 기업 평가를 실행해 항목별 점수·근거 상태·한계점이 포함된 결과 확인
- 테스트, 실행 방법, 구조를 포함한 README 정리
- 기능 브랜치를 `develop`에 통합한 뒤 기본 브랜치 `main`에 반영

## 배우고 느낀 점

처음에는 RAG를 단순히 “문서를 넣고 질문하면 답해주는 기능” 정도로 생각했다. 직접 구현해 보니 실제 품질은 문서 수보다도 전처리, 청킹, 임베딩, 검색 평가, 출처 관리에서 크게 달라졌다.

또한 Agentic RAG의 핵심은 에이전트의 개수가 많다는 데 있지 않았다. 어떤 상황에 어떤 도구를 사용할지, 검색이 실패했을 때 어디까지 다시 시도할지, 언제 종료할지를 명확하게 설계하는 것이 더 중요했다.

이번 프로젝트를 통해 다음 세 가지를 가장 크게 배웠다.

1. 검색 품질은 추측하지 말고 평가셋으로 측정해야 한다.
2. LLM이 잘하는 해석과 코드가 잘하는 계산을 분리해야 한다.
3. 좋은 결과뿐 아니라 근거 부족과 한계도 함께 보여줘야 신뢰할 수 있다.

## 다음에 개선하고 싶은 점

- 평가 질문과 정답 데이터를 늘려 검색 성능을 더 안정적으로 측정하기
- 웹 검색 결과의 출처 등급과 최신성 검증 강화하기
- 기업별 평가 결과를 한눈에 비교할 수 있는 화면 만들기
- LLM 호출 비용과 전체 실행 시간 측정하기
- 실제 투자 전문가의 검토를 받아 평가 기준과 임계값 보완하기

이번 프로젝트는 투자 결정을 자동으로 대신하는 시스템이 아니라, 공개 근거를 체계적으로 모으고 후속 실사 대상을 정하는 데 도움을 주는 도구다. 아직 개선할 부분은 많지만, RAG 검색부터 멀티 에이전트 협업, 규칙 기반 판정과 보고서 생성까지 하나의 흐름으로 연결해 봤다는 점에서 의미 있는 실습이었다.
